# Close tab discards; reload resumes

Proposed implementation design, 26 October 2026; tightened against the independent close-plan review of quota source `a08535da641fce85a3c66224e62d7611cf478f25`. That source is frozen for quota qualification, not lifecycle implementation evidence. After quota publication, record the actual new baseline and implement in the current isolated checkout; no extra worktree is required. This document makes no source, database or deployment change.

## Approved behavior and present gap

The owner's latest instruction makes **closing the preparation's browser tab an exit/discard request**. Switching to another tab, minimizing, opening another app, changing Accounts inside a batch and PDF/email stage changes keep the work. F5/reload still resumes the same active preparation with its latest PDF and compose edits. Existing actual Sent, Gmail Draft, unknown provider result, admitted generation/upload and shared-reference protection remains authoritative.

This supersedes earlier statements in `DECISIONS_AND_OPEN_ITEMS.md` that browser closure is never a discard instruction. It does not authorize an old-job purge, idle timeout, lost-heartbeat cleanup, provider calls, email sends or changes to financial/history data.

Today `BatchRoute` saves identities/layout/common-message envelopes in sessionStorage; its PDF sessions are in Maps/React memory. `DocumentRoute` restores only in-memory `initialSession`. `pdf/editor-session.ts` explicitly excludes browser serialization. Separate-email unsaved fields are component state. Thus existing F5 support does **not** establish preservation of the latest unsaved PDF/individual message. This change needs a temporary local tab checkpoint as well as close handling. It must not create a cloud saved-editor project, Documents backlog or user-managed saved-project feature.

## Browser evidence and unavoidable limit

The [Navigation API specification](https://html.spec.whatwg.org/multipage/nav-history-apis.html#the-navigation-api) supplies outgoing `navigate` events and `navigationType='reload'`; feature-detect and qualify actual browser behavior. `PerformanceNavigationTiming.type` describes how the current document arrived and must never classify its outgoing exit. The [Chrome Navigation API guide](https://developer.chrome.com/docs/web-platform/navigation-api) describes its central navigation signal; listen without intercepting normal browser reload.

[pagehide](https://developer.mozilla.org/en-US/docs/Web/API/Window/pagehide_event) is not guaranteed, particularly during mobile/process termination. It carries a bfcache flag, not a close-versus-reload reason. [beforeunload](https://developer.mozilla.org/en-US/docs/Web/API/Window/beforeunload_event) is cancellable and unreliable; never submit discard from it. A missing navigation event is only a qualified browser heuristic, not a universal close API.

**No ordinary webpage can guarantee both immediate cleanup on every close/crash and preservation on every arbitrarily slow reload, especially without Navigation API support.** Do not use a grace timeout or missing heartbeat to pretend otherwise. Qualified normal desktop close is best effort; ambiguous/unsupported/no-event cases retain work. A durable accepted close command can retry safely, but no server can recover a close instruction it never received and that the browser never persisted. State this limitation in release evidence.

## Design

### 1. Ephemeral reload checkpoint

Use one local checkpoint coordinator for single `DocumentRoute` and `BatchRoute`. Stable identity is `session.user.id` (real actor) plus the existing authentication-tab storage key, with workspace owner and regional grant separate. A rotating access token is request authorization, never a cache/session key. Add a narrow preparation-tab initializer with its own random ID and encryption key in sessionStorage: preserve these only on verified reload or approved same-tab auth return; non-reload/opened/duplicated tabs discard copied preparation identity and register a distinct claim. Existing `access/tab-session.ts` is authentication initialization, not a preparation identity service. If copied-tab provenance is ambiguous, keep preparation protected/read-only until a distinct claim is obtained. Never use a shared localStorage active-tab pointer. Check server close/outbox tombstones before decrypting a browser-restored tab.

Checkpoint only current PDF content, bounded Undo/Redo, selected Account/page and layout; raw filename drafts/inline text input; separate recipients/subject/body/rich text/names/stage and combined raw `recipientText`/message; and exact attachment receipts. No arbitrary component state, preview-render cache or general save-for-later feature. Preserve pending save commands only where the existing path is genuinely idempotent. Separate-email revision PUT is not automatically replayable: retain content, fetch current revision and require normal human retry if its outcome is uncertain. Never replay send/print/upload or store credentials/test recipients.

Restore fetches fresh authorized job/source receipts and rejects closed, discard-requested, manifest/source/revision mismatch. Reuse `pdf/load-job-sources.ts` byte-count/SHA checks. The existing supplemental buffer-object-identity check cannot validate deserialized bytes: the checkpoint codec must verify persisted supplemental digest/size/type and then reconstruct the normal runtime objects. Retain source-model validation. Review approval requires the exact reviewed export receipts/bytes; restoring edits alone never grants review. Uncertain reviewed-file upload reconciles its existing receipt without another upload or source generation.

Store immutable image/data-URL/supplemental assets once in encrypted IndexedDB; persisted project/history uses asset references and restore materializes the existing runtime shape. Do not duplicate original source PDFs: reload those through exact authenticated receipts. Journal concrete changed fields/pages and history transitions with base/result revisions, not whole project snapshots or geometry commands to rerun. Proposed bounds are 256 KiB aggregate and 64 KiB/item, subject to representative synthetic size/latency qualification within existing model/memory limits. Compact before exhaustion and remove only a prefix whose snapshot transaction committed. New asset dependencies must persist before their referencing edit is accepted; oversized changes use the explicit acknowledged large-commit path. Never wait until unload to serialize a PDF.

One editor-local accepted-transition adapter applies validation, project/history change and review invalidation together. Keep existing `commit` synchronous/boolean for small changes and preserve voucher reflow/caller behavior; do not silently turn it into a Promise. Drag preview remains in memory; pointer-up validates and journals the final transition before accepting it. Undo/Redo journal resulting state/history changes, not replayed geometry. Oversized transitions use a separate busy async path, serial admission and expected local revision/source fences so a delayed IDB completion cannot overwrite later work. A trailing React effect is never the only checkpoint.

Raw child inputs journal on change, including `FilenameField` before Apply/blur, PDF inline fields and combined recipient text. On storage denial retain visible raw input plus prior durable state, show non-durable status and retain beforeunload warning; never drop the final character or claim it persisted. Uncompleted gestures/failed transactions are not committed edits. Measure representative existing near-limit project/asset/history cases without introducing a benchmark subsystem.

Bulk encryption with a per-tab sessionStorage key protects orphaned local data, not against XSS. The synchronous journal stays in tab-scoped sessionStorage. Delete only exact session checkpoint material after reconciled close/discard/completion or sign-out; invoking keepalive alone is not acknowledgment. Orphaned encrypted blobs may be collected by exact local session IDs without server-job deletion. Local pending-close tombstone blocks restore until that same command is reconciled.

### 2. Qualified close command and durable cleanup

Register a bounded exact manifest while alive: real actor/workspace owner/region, existing jobs and source revisions, or create-command UUID plus immutable create-payload digest. Return an acknowledged manifest revision before starting that work. Batch maximum remains 20 groups; replacement creates use the same seam. This lifecycle metadata is limited to preparations; do not instrument every customer runtime action.

Both `CreateDocumentDialog` and `BatchRoute.createEntries` pass `{sessionId,epoch,manifestRevision}` with existing create input. A service-only create-admission RPC takes the same claim/open/close locks, validates registered command/payload/actor/scope, calls existing `ar_document_create_v5` and binds its job in the **same transaction**. A later frontend attach is insufficient. Close first refuses a new create; an already admitted create remains attached even if its response is lost. Before dispatch, check the same durable closure/admission state; preserve already-started/uncertain generation and route it through existing pending/finalize behavior. Cleanup includes eventual jobs from admitted commands, never all jobs for an Account.

Use fixed same-origin endpoints under `/api/documents/tab-sessions`: register/claim/resume and `POST /api/documents/tab-sessions/{sessionId}/close`. Validate real actor and member regional permission before shared-owner mapping. Claim/open/close/abandon decisions share atomic locking so close cannot race a newly admitted other-tab claim. Reload obtains a new epoch only for an active, non-closed session. A new old-epoch close conflicts; accepted definitive close cannot reopen. Another live claim releases only this tab's claim and gives terminal protected outcome for this command, not a timer waiting for the other tab to disappear. Never expire a claim into discard from heartbeat loss.

The close body is `{commandId, epoch, manifestRevision}` (UUID command, integer revisions), maximum 2 KiB. It references the server-verified exact manifest, never arbitrary object keys, invoice lists, URLs or deletion targets. Require current app Bearer authentication and same-origin Origin; reject cross-site Fetch Metadata and redirects. Service-only RPCs recheck real actor/session membership with atomic row/advisory locks. No anonymous bearer-in-URL/body trick or provider credential is added.

One app-level listener owns outgoing navigation state and reads the latest token from a ref at dispatch. A current `navigate` reload suppresses close for that navigation, however slow its successor bootstrap. Clear only proven cancellation/abort/error or continued same-page navigation state, never a timeout on a real reload. Same-document Account/stage transitions, hash changes, downloads, address-bar non-reload navigation, visibilitychange, blur, freeze and persisted pagehide do not authorize tab-close discard. Arrival `PerformanceNavigationTiming.type` may remain in authentication initialization; it is forbidden only as outgoing-close classification. Explicit in-app Exit retains existing acknowledged abandon behavior.

Enable destructive classification only for actual qualified desktop Edge/Chrome event sequences, including both dirty-warning and no-warning paths. On qualified normal close (pagehide persisted=false with no current outgoing navigation, after any cancellable beforeunload completes), synchronously write a bounded **localStorage** metadata outbox keyed by real actor/session/command, then send one authenticated same-origin `fetch` with `keepalive:true`, `redirect:'error'`. Do not attach an unloading AbortSignal or capture an old token. No asynchronous IDB write at pagehide is the sole outbox copy. Each body is ≤2 KiB, below the [aggregate Fetch keepalive limit](https://fetch.spec.whatwg.org/#http-network-or-cache-fetch); no PDF/text/save/provider action is included. Storage denial is an explicit best-effort limitation. Unsupported/ambiguous events never create a definitive close command.

After current actor authorization, the server looks up an existing command receipt and checks identical body **before** rejecting stale epoch: an accepted command remains retrievable after response loss. Changed-body replay conflicts. For new commands, validate epoch/manifest and atomically commit the close inbox receipt before response. A bounded processor delegates to existing `ar_document_abandon`/combined locks. Per-member states: `discarded` terminal; `protected` terminal for provider Draft/unknown/attempt history or other live claim; `pending` only for already admitted generation/upload/save awaiting safe completion. Never turn protected history into a future deletion. Existing finalization, exact retention receipts and deferred text cleanup remain. Scheduled maintenance retries durable pending work; `waitUntil` only accelerates it.

The localStorage outbox stores only schema version, real actor ID, session/command ID, epoch, manifest revision and creation time, bounded to 100 entries and 256 KiB. No shared active-tab pointer, token, customer names/text, PDF or provider response. It retries after the same actor authenticates using current authorization; remove exact entries only after receipt or terminal rejection is reconciled. If full, never evict an unresolved command to claim delivery. Pending-close local tombstone prevents immediate restored-tab resume until reconciliation; retain checkpoint material in that interval. Slow/lost response reuses the same command and never replays send/print/upload. OS kill with no persisted/received instruction remains protected; no additional no-event guarantee is claimed.

## Qualification and release

Use actual browser `page.reload()` and `page.close({runBeforeUnload:true})`, not only synthetic dispatched events. Playwright's [close documentation](https://playwright.dev/docs/api/class-page#page-close) notes that default close skips beforeunload and runBeforeUnload does not await actual closure; handle dialogs and await closure plus server receipt independently.

Prove immediate final edit/F5, accepted drag/Undo/Redo, raw filename/recipient input before blur, large assets/compaction failure, toolbar reload and delayed bootstrap; accepted/cancelled beforeunload, cancelled reload followed by close, no-warning close, actual toolbar/keyboard close and non-reload address navigation. Include window.open/duplicated copied sessionStorage, tab switching/minimize, bfcache, missing API, offline/expired auth, lost receipt/next-login retry, stale epoch/replay, atomic create/close and active-claim races, save/upload/send protection. Use fresh actual Edge/Chrome with an independent server observer and record versions/receipt outcomes separately. Include single/batch and separate/combined messages. Assert zero provider sends/prints and no duplicate uploads.

Use synthetic real-SQL fixtures for inbox/admission races and cleanup fences. Record normal-close support only for browser versions actually qualified; unsupported detection remains conservative. Do not purge existing sessions/preparations when enabling the feature. Deploy only after the separate quota work is complete, with a fresh baseline/review, then update decision/status documents with actual proof and platform limitations.
