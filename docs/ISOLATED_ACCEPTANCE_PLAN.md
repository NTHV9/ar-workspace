# Isolated final acceptance plan

> Completed on 11 September 2026. This is the original plan; actual results, provider boundaries and cleanup proof are in FINAL_ACCEPTANCE_20260911.md. The one Account/three Invoices and both temporary namespaces have been removed.

Owner-authorized Goal: create one synthetic AR Account with three Invoices, exercise the full app, fix defects, then remove only that scenario and its artifacts. This is additional final acceptance; it does not authorize OPERA ledger writes or real-customer test sends.

## Isolation decision (proposed implementation, not created yet)

Use two temporary, non-exposed schemas inside the confirmed existing Supabase project, containing **this rebuilt app's current schema/functions**, never the legacy app. No new paid project/backend. This keeps fake amounts out of normal business tables, source imports and reports. Suggested names are `ar_acceptance_20260911` and `ar_acceptance_private_20260911`; preflight must prove both absent. A tiny service-only registry/gateway in the real app identifies the scenario/owner and later records completion without customer data.

Clone schema definitions server-side (no data export): create empty app tables with LIKE INCLUDING ALL; reproduce FKs with rewritten app-schema references, functions via pg_get_functiondef, views via pg_get_viewdef in dependency order, and triggers via pg_get_triggerdef. Preserve RLS; revoke direct PUBLIC/anon/authenticated/service-role access to the temporary schemas. The gateway runs only approved app RPC names under the approved actor and exact scenario. Do not expose the schemas through PostgREST/global settings. Review defaults/sequences so test inserts cannot consume a real app sequence. Copy only non-secret app configuration required by the fixture (current collection rules/templates/Statement assets), never customer or provider-credential rows.

A service-only gateway invokes the same cloned business RPCs with typed named arguments. Worker backendRpc routes business calls to that namespace only in the verified scenario. Provider connection getters/refreshers, the confirmed Drive destination, auth and global Storage budget stay in the real app; never copy credential values. Direct Worker table reads require a small exact-table/filter allowlist using the gateway. Ordinary requests and scheduled work continue using the real schema.

Select the scenario with an authenticated, same-origin, HttpOnly cookie bound to its registry owner. All ordinary API authorization still runs. The app must prominently label the synthetic workspace. Invalid/inactive scenario cookies fail closed rather than silently reading/writing real business data. Provide an explicit exit action. No secret or temporary recipient enters Git; the one-time recipient comes from the authorized conversation and an ephemeral hash guard restricts every scenario send/draft to that address with no CC/BCC.

OPERA is never asked to create or read a fake account. A fixture source adapter supplies exactly three synthetic Invoices and their test PDFs. Both source type and PDF contents identify the test. The real Statement renderer/editor, settings, billing rules, collection policy, reports, histories, email evidence verifier, remittances, Drive and private Storage execute against the isolated business state. Real native Invoice API capability is separately established by the existing authorized native-PDF proof, not by synthetic files. Any call to a live OPERA reader from a scenario must be rejected.

For retention, use an isolated test clock only in the temporary retention SQL functions. Advance it after the synthetic work is complete and simulate a fresh zero-balance source observation in that isolated namespace. The actual provider objects must be precisely those recorded by the scenario; verify ID/owner/size/SHA and provider absence through the production adapters. Do not backdate real business rows or relax the production one-month criterion. Global quota guards remain active during every provider transfer.

## Acceptance sequence

1. Preflight schema/resource/cost/permission state; generate and locally replay the isolated definitions; prove normal queries never see the fixture.
2. Create the one Account/three Invoices and a private exact-ID artifact manifest. Verify Portfolio comparison/filter/sort/selection, Account fields/context and narrow screens.
3. Set synthetic Billing Required/term/contacts; exercise By Email and By System/manual history without altering real settings. Verify pinned due dates and billing/reminder history. Exercise hold/dispute/reopen/unknown balance and next-stage timing; future-date cases may be simulated, never reported as past real emails.
4. Selected-only A/C Statement plus explicit synthetic Invoice sources; PDF editing, all output arrangements, preview/acknowledgement/save/reopen; verify amounts unchanged in source state.
5. Real Gmail draft/send/evidence/thread paths only to the ephemeral authorized test address using synthetic content. No auto-send or new consumer recipient defaults. Preserve actual Gmail dates; do not alter them to make round timing pass.
6. Remittance three-line totals/attachments, reports/daily observations/history and actual Drive upload/readback. Simulate zeros/reopen only in the isolated source, verify retention blocks pending/shared/unknown work then deletes only eligible scenario bytes with its test clock.
7. Reconcile every provider result before cleanup. Remove exact scenario Supabase/Drive objects, exit the test workspace, and remove the two exact temporary schemas only after an identity/ownership preflight. Preserve the normal app and a minimal non-sensitive test summary. Gmail test messages may remain in the authorized mailbox as test evidence; do not delete mailbox content without a separately defined scope.
8. Final production smoke/auth/privacy/visual checks and latest-schema local recovery proof; update acceptance evidence and Goal only when remaining required work is handled.

This plan is not evidence that the scenario, gateway, schema copies, sends or cleanup have happened. Implementation must not silently substitute mocks for actual-provider evidence.

Implementation observation: OperaReader already accepts a third `FetchPort` constructor argument. A scenario-specific in-memory transport can exercise the existing readers/normalizers/selection checks with synthetic responses while refusing every unsupported request and never calling real OPERA. `makeReader` must take this explicit branch only for a verified scenario; it must not use real OPERA credentials in that branch. Native test PDFs remain conspicuously synthetic, and actual native API evidence remains the separately tested live path. This is preferable to duplicating source normalization or silently falling back on failures.

Direct RPC transports also exist in collection/policy-api, collection/api, settings/api and documents/api; route these through the same checked scenario gateway, preserving their existing size/error/actor guards. Direct REST table reads in Worker/index, document listing and previousInvoices require exact-scope handling too. Budget and provider-connection transports must remain on the real control plane. Workflow parameters must carry only a validated scenario ID, then reload its owner/state before reconstructing scoped bindings; never serialize credentials in durable step data.

## Required artifact isolation refinement

The temporary business schemas alone are insufficient: a caller could deliberately reuse an existing object path. Use a **separate private test Storage bucket** (`ar-acceptance-files`, prove absent first) and a newly created app-owned test subfolder inside the confirmed Restricted Drive folder. Rewrite only the cloned functions' bucket literal to the test bucket. Scope-aware file helpers and retention adapters must insist on the bucket/folder selected by the verified session, never accept an arbitrary target. Original files cannot become targets of the accelerated test clock, even if identifiers are reused.

Keep one conservative reservation in the **real global budget** for the entire scenario before provisioning: proposed bounds40MiB stored files,80MiB managed egress,24MiB DB growth. Keep it started until exact cleanup/settlement is proved. A private per-file budget journal in the test namespace accounts for its own fixed test bucket, using tighter actual caps (e.g.16MiB stored,64MiB egress), plus an explicit measured schema-size limit below the globally reserved DB bound. No timer releases uncertain reservations. Settle the global reservation only from verified cleanup, counted transfers and bounded DB measurements; incomplete results keep the reserve. This prevents test traffic from escaping the main cost guard without requiring object-key sharing between buckets.

Provider connection credential getters/refreshers remain on the real control plane. The test Drive **destination metadata** belongs to the isolated schema and points only at the new restricted test subfolder; do not copy the real root as the test destination. Check the original parent before creating that subfolder and delete only exact test files, then the verified-empty exact test folder.

Preserve a minimal non-sensitive summary of real test Gmail receipt IDs/timestamps in the real acceptance-session audit before dropping the isolated schemas. No body, address or customer/default-contact data is retained there. The normal recovery audit must recognize those IDs as completed isolated tests rather than falsely reporting lost business receipts after cleanup. Test messages themselves are not deleted from Gmail by this plan.

The scope-aware routing, fixture transport, cookie, artifact isolation, clock and scenario have not been implemented/applied yet; only the isolated-definition/gateway draft has passed local replay. Do not claim provider acceptance from that schema test.
