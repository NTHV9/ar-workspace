# Workspace-generated Invoice — 21 September 2026

The owner explicitly chose the Statement approach for Invoice: generate PDFs in AR Workspace from the six privately supplied hotel RTFs, while retaining OPERA as the financial source. New preparations use this source; existing jobs, reviewed bytes, Drafts and uncertain deliveries retain their original source.

## Verified financial mapping

- AR account/detail reads verify Hotel + Account + transaction + invoice + folio and the current balance. The balance is checked again after the slower charge/tax reads.
- AR `invoicePostings` requires the verified internal Folio window and `AccountId` context. It returns the invoice's charge rows without the reservation's City Ledger settlement credit.
- The printed Reference is `checkNo`, not the posting transaction identity. Hash comparison with the two supplied native references matched all 27 rows (14 KAT, 13 WAKL).
- Cashiering `financialPostingsNetVat` has a verified **50-row limit** and returns the requested offset, unlike the separate invoicePayments next-offset contract. Complete pagination, stable totals and unique transaction identities are required.
- Package wrappers and their underlying charges share `referencePackageTransactionNo`. The original package reference is distinct from the visible wrapper posting identity. Only the selected package's components are counted, with gross reconciliation for every selected line.
- Actual generated tax postings identify VAT (`TAX` group + VAT description) separately from Service Charge (`SVC`). Fractional tax amounts are accumulated before rounding once to satang. Missing/unknown/non-reconciling breakdowns are rejected, not estimated. The supplied templates' 7% caption is enforced against the verified rate.
- Outstanding is the fresh AR balance, independent of gross/partial payment. Service Charge remains in the taxable pre-VAT amount. Explicit non-taxable breakdowns remain separate. No accounting, settlement, print or email operation is used.
- Optional payer tax number is used only when the selected internal window and AR profile identity agree.
- Reservation header reads verify the exact Hotel + Reservation and explicitly disable recently-accessed/session side effects. The five CUSTOM_REFERENCE templates use the reservation's `customReference`; KAT retains its AR reference with the explicit custom reference as a fallback. The live WAKL custom-reference hash matches the supplied Voucher exactly. Confirmation and ParentReservation IDs are never used as vouchers. First-name/surname ordering is used only for a matching Invoice guest profile. [Oracle Reservation API contract](https://github.com/oracle/hospitality-api-docs/blob/main/rest-api-specs/property/v1/rsv.json).

Both exact live comparison selections passed model and generated-PDF verification: charge totals, VAT, pre-VAT totals, non-taxable totals, AR outstanding, every printed Reference and Voucher match the supplied native Invoice pages. Both final source PDFs were opened in the signed-in web app and their headers/footers inspected. Real values and identifiers remain outside Git.

## Template and document integration

`scripts/invoice-template-assets.py` prepares private, versioned assets from KAT, TSK, TLKL, WAKL, TLFO and TSAN RTFs. The existing local LibreOffice conversion is only a preparation tool; production rendering uses the already-installed pdf-lib/fontkit/Thai font on Workers. No paid dependency or new service.

Title, header labels/colons, all five table headings, row values and total captions/amounts remain real PDF text. This preserves source editing, an editable empty Voucher target, and all five new-row cells even when the selected row has no credit. The Voucher detector accepts both INVOICE and historical COPY OF INVOICE headings with the same strict Folio/colon checks. Logo/banking/footer artwork stays private. A clipped hard break in KAT's bank-name cell is rendered as the complete fitted source text. Multi-page output repeats identity/header/columns and groups the closing totals and signature. Final active template version is `invoice-rtf-20260921-v2`; v1 is retained for preparations already bound to it.

`ar_document_create_v5` snapshots Invoice source + template version into new jobs and fingerprints. It delegates through the existing actor/hotel, selection, atomic refresh, transient lifecycle and execution-queue checks. Replays of older commands join the older job. Existing source/version fields cannot change, and an existing command retains its original version after a new template becomes active.

Invoice templates live in `ar_private.invoice_templates`, with RLS and no anon/authenticated table grants. Only the service role can call the exact hotel/version getter. No customer PDF/JSON, banking asset or credential is stored in Git or a public browser bundle. The six initial assets occupy approximately 1 MB in the existing database; the database was about 124.5 MB before this increment.

## Mixed POS tax postings and transient reads — 21 September 2026

The six-hotel reliability sweep found a real mixed Invoice with 76 selected AR rows and 104 Cashiering rows over three pages. It combined package-generated VAT with separately posted POS revenue, service charge and VAT. OPERA legitimately omitted the optional `postingBreakdown.taxes` array on the latter rows; treating that omission as a missing source caused preparation to fail.

The adapter now accepts an omitted taxes array while still requiring gross = net + all returned generates. Separate VAT is identified by the exact Hotel/transaction-code definition (`TAX` group and VAT description), reconciled with the same posting date and nonempty printed check, and summed from the actual postings. A receipt's rounded net/service/VAT rows must agree with 7% within one satang. This tolerance validates the rate only: it never computes replacement tax or rounds an estimated base. Embedded and separately posted tax identities share duplicate protection. Missing matching receipts, unsupported tax codes, different scopes and non-reconciling amounts remain errors. Non-taxable lines stay separate.

For transient duplicate/changing/incomplete pagination, the reader makes at most three complete attempts. Every attempt revalidates the account and restarts all pages; no rows from a failed read are deduplicated or reused. Fresh AR balance fencing remains, and model failures or balance changes are not retried. Rendering and storage happen once, only after a complete verified model. Existing failed/ready preparations are retained unchanged.

Two original production failures had `duplicate_member`; the exact original responses were unavailable. Repeated reads and a real button-created replacement succeeded before the fix. Bounded whole-read recovery addresses this observed transient failure class; within-page versus cross-page causation is not claimed. The private read-only diagnostic now distinguishes read stages and aggregate duplicate categories without returning source rows or customer/check identifiers.

Verification: 1,357 unit tests plus final targeted tests/typecheck/build/assets/dry run; three deployed editor integration cases (synthetic APIs/PDFs); live representative Invoice reads across KAT, TSK, TLKL, WAKL, TLFO and TSAN. Both originally failed selections and the additional mixed-POS selection produced ready PDFs through Create document job. The mixed-POS PDF's three pages and footer were inspected; the model verified 76 AR rows against 104 source rows. KAT/WAKL reference checks remain valid. This does not claim every historical invoice shape is covered. No failed preparation was overwritten/discarded and no email, billing record or OPERA accounting mutation was made.
