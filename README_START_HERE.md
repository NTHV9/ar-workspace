## ใช้ชุดนี้อย่างไร

1. แตก ZIP ลงโฟลเดอร์โครงการใหม่ที่อยู่นอกโครงการเดิม เช่น `D:\Projects\katathani-ar-workspace` ชื่อนี้เป็นตัวอย่าง ไม่ใช่โครงการที่สร้างไว้แล้ว
2. เปิดโฟลเดอร์ใหม่นี้เป็น Project/Workspace ใน Codex และเริ่มแชทใหม่
3. อ่าน `AGENTS.md` และ `docs/PRODUCT_SPEC.md` ก่อน แล้วอ่านไฟล์ประกอบตามลำดับด้านล่าง
4. นำภาพต้นแบบ 7 ภาพมาใส่ `references/design/` และนำคำอธิบายดีไซน์จากแชท Codex เดิมมาเพิ่ม โดยดูรายการใน `docs/DESIGN_HANDOFF.md`
5. ใช้ข้อความใน `prompts/02_START_NEW_CODEX.md` เพื่อเริ่มงานใหม่อย่างมีขอบเขต
6. ให้ Codex รายงานความเข้าใจ แหล่งคำสั่งที่อ่าน ไฟล์ที่หาไม่พบ ประเด็นต้องพิสูจน์ และแผนงานก่อนเขียนแอป

## สิ่งที่อยู่ในชุดนี้

- `AGENTS.md`: กติกาทำงานสำหรับโครงการใหม่และลำดับการอ่าน
- `docs/PRODUCT_SPEC.md`: ข้อกำหนดธุรกิจล่าสุดที่รวบรวมจากแชท
- `docs/DECISIONS_AND_OPEN_ITEMS.md`: สิ่งที่แทนข้อเสนอเก่า ข้อเสนอที่ยังไม่ล็อก และข้อมูลที่ยังขาด
- `docs/INTEGRATION_VALIDATION.md`: API และจุดที่ต้องทดสอบจริง ไม่ใช่คำรับรองว่าต่อสำเร็จแล้ว
- `docs/DESIGN_HANDOFF.md`: รายการดีไซน์ต้นแบบและวิธีรับคำอธิบายจาก Codex เดิม
- `docs/ACCEPTANCE_CHECKLIST.md`: ตัวอย่างการตรวจรับตามข้อกำหนดใหม่
- `docs/PROJECT_STATUS.md`: สถานะเริ่มต้นที่ยังไม่อ้างว่าทำอะไรสำเร็จ
- `prompts/01_EXTRACT_DESIGN_FROM_OLD_CODEX.md`: ข้อความให้แชทเดิมสรุปเฉพาะดีไซน์
- `prompts/02_START_NEW_CODEX.md`: ข้อความเริ่มงานในโครงการใหม่

## สิ่งที่ไม่ได้อยู่ในชุดนี้

ไม่มีภาพ PNG ต้นแบบทั้งเจ็ด ไม่มีคำอธิบายจากแชท Codex เดิมที่ยังไม่ได้ส่งมา ไม่มี JSON/PDF ลูกค้าจริง ไม่มี Secret/Token/Password ไม่มี Folder ID หรือ Cloud project ID และไม่มีอีเมลผู้รับทดสอบแบบใช้ครั้งเดียวที่ผู้ใช้ขอไม่ให้จำ

ต้องย้ายหลักฐานและไฟล์อ้างอิงเหล่านั้นอย่างตั้งใจ ไม่ถือว่าแนบครบแล้วเพียงเพราะมีชื่อไฟล์ในเอกสารนี้

## ขอบเขตความน่าเชื่อถือ

นี่เป็นการสังเคราะห์ข้อกำหนดล่าสุดจากบทสนทนาที่มีให้เห็น ไม่ใช่ transcript ทุกข้อความ และไม่ใช่การรับรองว่าคำอธิบายทางเทคนิคเก่าของผู้ช่วยทุกข้อความถูกต้อง รายการ API/ข้อจำกัดของผู้ให้บริการที่ยังไม่ได้ทดสอบถูกแยกไว้ใน INTEGRATION_VALIDATION และ OPEN_ITEMS

จุดที่ผู้ใช้ยืนยันล่าสุดใช้แทนข้อเสนอที่ขัดกันก่อนหน้า ส่วนที่ผู้ช่วยเสนอแต่ยังไม่มีคำยืนยันเฉพาะ ให้คงสถานะเป็นข้อเสนอ ไม่แอบเพิ่มเป็นกฎบังคับ

## หลักของโครงการ

สร้างใหม่ทั้ง Frontend, Backend, schema, integration, tests และ deployment ไม่คัดลอกโค้ด/โครงสร้างจากแอปเดิม ไม่ใช้โครงการเก่าเป็น runtime dependency

เก็บโครงการเดิมไว้แบบอ้างอิง ไม่ลบข้อมูล โฟลเดอร์ OAuth หรือบริการเดิมเพียงเพราะเริ่มใหม่ ใช้บริการ Cloudflare/Supabase ที่ผู้ใช้มีอยู่ได้หลังยืนยันปลายทาง ไม่สร้าง project เสียเงินเพิ่มหรือ reset ฐานข้อมูลโดยอัตโนมัติ
