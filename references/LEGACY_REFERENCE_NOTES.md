## ข้อค้นพบที่ยังมีประโยชน์

### ข้อมูล OPERA และตัวตนรายการ

- ระบบเดิมเคยบันทึกการอ่าน OPERA และเผยแพร่ข้อมูล KAT/TSK สำเร็จ แต่หลักฐานนั้นไม่รับรอง integration ของระบบใหม่ ต้องพิสูจน์ response และความครบตาม `INTEGRATION_VALIDATION.md` ใหม่
- ยอด Account/Aging อาจมีข้อมูลในขณะที่ตาราง Invoice/Folio ว่าง ตรวจทั้งข้อมูลต้นทาง การอ่านครบทุกหน้า และการแปลงข้อมูล อย่าคิดว่า “ไม่มีแถว” แปลว่า “ไม่มีหนี้” หรือสร้างแถวชดเชยเอง
- รักษา Hotel + Account + Item identity และแยก Account ID, Account No. และชื่อให้ชัด ชื่อหรือเลขเหมือนกันข้ามโรงแรมไม่เป็นหลักฐานพอสำหรับรวม ledger
- อ่านวันที่ธุรกิจของแต่ละโรงแรม แยกวันที่บิล วันที่ส่งจริง วันที่ชำระ และเวลาที่ดึงข้อมูล ไม่ใช้เวลา capture แทนวันที่ธุรกิจ
- Pagination ต้องตรวจสมาชิกซ้ำ/ตกหล่นและข้อมูลเปลี่ยนระหว่างหน้า ผลรวมตรงอย่างเดียวไม่ยืนยันว่ารายการครบ

### Billing workbook และค่าตั้งเดิม

- เจ้าของเคยให้ workbook ใน Downloads ชื่อ `แบบฟอร์มข้อมูล Agent วางบิล & ทวงหนี้.xlsx` และให้ใช้คอลัมน์ G (Billing Type): `By Email` → `REQUIRED`; ค่าว่างและ `By System` → `NOT_REQUIRED`
- มีคำแก้ไข Account No. หนึ่งเซลล์จากเจ้าของหลัง workbook รุ่นเดิม ต้องตามคำแก้ไขจากแหล่งส่วนตัวก่อนนำเข้าใหม่ ไม่บันทึกเลขบัญชีลูกค้าไว้ใน handoff นี้
- checkpoint เดิมบันทึก mapping 57 แถว: 50 Required และ 7 Not Required แบบสืบทอด รวมทั้ง preflight เทียบ OPERA ครบ 57 แถว นี่เป็นหลักฐานเตรียม mapping เดิม ไม่ใช่คำรับรองว่านำเข้าสู่ระบบใหม่หรือใช้จริงครบแล้ว
- ควรรักษา workbook ต้นฉบับ คำแก้ไข และ mapping ส่วนตัวเดิมไว้ แล้วตรวจ Account ID/No./Hotel ใหม่ก่อนออกแบบ import ไม่คัดลอก mapping หรือ secret payload มาในโฟลเดอร์นี้
- Required flag, Term, ผู้รับ และ defaults เป็นข้อมูลธุรกิจที่ควรรักษาแม้ยอดเป็นศูนย์ การย้ายค่าจริงเข้าระบบใหม่ต้องกำหนดแยกภายหลัง ไม่ทำอัตโนมัติในรอบนี้

### Gmail, OAuth และสถานะหน้าจอ

- ระบบเดิมเคยเจอ `redirect_uri_mismatch` และ redirect ไป internal origin หลัง OAuth สำเร็จ บทเรียนคือใช้ callback/origin ที่ตั้งไว้ตรงกัน และตรวจ URL ที่กลับถึงผู้ใช้จริงหลังอยู่หลัง proxy
- Login ของเว็บกับสิทธิ์ Gmail เป็นคนละส่วน การเปลี่ยน hosting/login ของระบบใหม่ไม่แปลว่าต้องลบ Google OAuth client หรือสิทธิ์กล่องงานเดิม
- checkpoint เดิมบันทึก callback สำเร็จและ connector persistence แล้ว แต่ delivery ถูกปิดไว้ได้ หน้าจอควรแยก “เชื่อมบัญชีแล้ว” จาก “พร้อมส่งอีเมล” อย่าบังคับเชื่อมซ้ำเพียงเพราะ delivery ถูกปิด
- Draft ไม่เท่ากับ Sent และ Draft หายไม่ใช่หลักฐานการส่ง หากตอบกลับไม่แน่นอนให้ตรวจผลเดิมก่อนเริ่มคำสั่งใหม่ การ restore ฐานข้อมูลไม่ย้อนอีเมลที่ส่งจริง
- สิทธิ์และการยินยอมที่เคยทำไว้เป็นข้อมูลประวัติ ต้องตรวจใหม่เฉพาะส่วนที่เปลี่ยน origin/client/scope ไม่ถือว่าการทดสอบใหม่ผ่านแล้ว

### เอกสารและคุณภาพ UI

- สถานะ HTTP สำเร็จหรือลิงก์รายงานยังไม่พิสูจน์ว่าได้ PDF ถูก Hotel/Account/Invoice ต้องตรวจ bytes และรายการที่เลือกจริงก่อนใช้
- อย่า map Invoice No., Folio No. และ internal window ID จากชื่อที่คล้ายกัน และอย่าเปลี่ยนยอดบน PDF ต้นฉบับเพื่อให้ validator ผ่าน
- การทดสอบจำลองเดิมเคยผ่านทั้งชุด แต่การตรวจเส้นทางภายหลังพบเมนู 404 และปุ่มไม่มี handler ระบบใหม่ควรตรวจทุกเมนู/ปุ่ม เส้นทางจริง การกลับหน้าเดิม และ loading/empty/error พร้อมเทียบ screenshot กับต้นแบบ
- ภาพเป็นหลักฐานด้านดีไซน์ มีข้อมูลสมมติ ไม่ใช่ผลรับรองความถูกต้องของยอดหรือกฎงานล่าสุด เก็บ PNG เดิมและปรับ implementation ให้ตรงสเปกใหม่
- เมื่อคำสั่งอาจสำเร็จแล้วแต่ response หาย การเปลี่ยนหน้า/รีโหลดอาจทำให้ key ในหน่วยความจำหาย ต้องออกแบบการกู้ผลคำสั่งและการป้องกันซ้ำให้เหมาะกับระบบใหม่ ไม่ยกกลไก legacy มาใช้ทั้งชุด

### Backup และเครื่องมือทดสอบ

- checkpoint เดิมบันทึก backup ล้มเหลวและการเปิดเว็บกลับสำเร็จ ยังไม่ใช่หลักฐานว่า restore ระบบใหม่ทำได้
- การทดสอบเดิมพบ PostgreSQL client/server คนละ major version ทำให้ dump/restore ล้ม ต้องตรวจรุ่นเครื่องมือและขอบเขตไฟล์ที่ backup ครอบคลุมจริง
- ใช้บทเรียนเรื่องการตรวจผล restore และการไม่ส่งซ้ำ ส่วนจำนวน migration, schema, ขนาดเครื่อง, retention, receipt, วันที่ห้าม retry และ CI gates เฉพาะระบบเก่าไม่ใช่ข้อกำหนดระบบใหม่

## ข้อมูลและบริการเดิมที่รักษาไว้

| สิ่งที่รักษา | หลักฐานเดิม / การใช้อ้างอิงต่อ |
|---|---|
| โฟลเดอร์ AR DB, Git history, branches, worktrees, งานที่ยังไม่ commit และ `.impeccable` | เก็บไว้ทั้งหมด มีทั้งหลักฐานดีไซน์และงานที่ยังไม่เสร็จ ไม่คัดลอกมาเป็นฐานแอปใหม่ |
| OPERA environment และสิทธิ์ KAT/TSK | ยังเป็นแหล่งข้อมูลเงินและเอกสาร ตรวจปลายทาง/สิทธิ์ใหม่อย่างตั้งใจก่อนใช้ |
| Google OAuth/API และกล่องงานกลาง | รักษา client, grants และ mailbox state; เปลี่ยน callback เฉพาะเมื่อรู้ปลายทางใหม่ ไม่ revoke/reset ในรอบเตรียม |
| Shared Drive และไฟล์เดิม | เก็บโฟลเดอร์จริงและ file references; ห้ามล้างจากชื่อหรือย้ายไฟล์เอง สิทธิ์ archive/purge เคยแยกกัน แต่ต้องตรวจจริงก่อนใช้ใหม่ |
| Secret Manager และ Windows Credential Manager | รักษาค่าเดิมไว้ที่เดิม รวมทั้ง key versions ที่อาจใช้ถอดรหัสข้อมูลเก่า ไม่อ่านหรือคัดลอกค่าลับในรอบนี้ |
| Cloud Run, Cloud SQL, Artifact Registry, Scheduler, Pub/Sub, monitoring และ state/evidence storage เดิม | เปลี่ยนสถาปัตยกรรมใหม่ไม่ใช่อนุญาตให้ลบของเก่า; checkpoint ล่าสุดที่อ่านรายงานว่าเว็บ OPEN, providers ปิด และ Scheduler 7 งาน paused แต่ไม่ได้ยืนยันสถานะสดวันที่ 8 กันยายน |
| ฐานข้อมูล/config/history/receipts/backups เดิม | รักษาไว้เพื่อสอบทานและตัดสินใจย้ายข้อมูลภายหลัง ไม่ import schema หรือ business state อัตโนมัติ |
| Workbook Billing และเอกสาร/PDF/หลักฐานลูกค้าส่วนตัว | รักษานอก Git และนอก packet นี้ ใช้แหล่งส่วนตัวเมื่อได้รับคำสั่งในขั้นที่ต้องใช้ |
| Cloudflare และ Supabase ที่เจ้าของมีอยู่ | สเปกใหม่แจ้งว่ามีบริการแล้ว แต่ packet ไม่มี target IDs และรอบนี้ไม่ได้เชื่อมตรวจ ไม่เดาปลายทางหรือสร้าง project เพิ่ม |

## จุดที่สเปกใหม่ใช้แทนของเดิม

Cloudflare/Supabase, ไม่มี auto-send/auto-draft, refresh 07:00/19:00 + manual + on-open ตามเกณฑ์ใหม่, ผู้รับตั้งเองไม่มี OPERA fallback, PDF ปกติจาก OPERA และไม่มี silent system fallback, การจัดไฟล์สามรูปแบบ, Google + Password login, Follow 3/Final/Urgent, นับ latest sent stage ต่อ Invoice, และ CLEARED เมื่อยอด Invoice เป็นศูนย์ที่พิสูจน์แล้ว ให้ยึดเอกสารใหม่ทั้งหมด

กฎเดิมเรื่อง RPO/PITR/retention, M6, Cloud Run commissioning, restore/cutover, locked migration counts และรูปแบบ schema ไม่ถูกนำมาเป็น gate ของโครงการใหม่ การไม่ทำแผนเก่าต่อไม่ใช่การอ้างว่าแผนเก่าผ่านแล้ว

## สิ่งที่ไม่ได้ทำในรอบเตรียมนี้

ไม่ได้แก้ไฟล์เดิม เปลี่ยน branch, pull/fetch/reset, commit/push, ทดสอบแอปเดิมต่อ, ติดต่อบริการ, อ่าน secret, deploy, แก้ฐานข้อมูล หรือส่งอีเมล โครงการใหม่มีเฉพาะเอกสารและภาพที่อนุญาต ตรวจรายการได้ใน `HANDOFF_VERIFICATION.md`
